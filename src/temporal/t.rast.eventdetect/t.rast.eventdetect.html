DESCRIPTION

t.rast.eventdetect detects and counts relatively rapid changes ("events") in a space-time raster dataset (strds) and characterizes the recovery after each event. It works per pixel on the raw, irregularly spaced observations, using the actual acquisition dates and keeping the cloud gaps (NULL values) in place. Missing observations are never filled: a comparison is simply made against the last clear observation. This makes the module suitable for gappy optical time series such as Sentinel-2 vegetation-index composites.

The method generalizes the grassland mowing-frequency approach of Kolecka et al. (2018). Mowing is one use case; the same logic applies to any abrupt disturbance and recovery (harvest, flood or hail defoliation, fire, drought die-back) and, with direction=rise, to rapid increases such as green-up.

Do not feed a smoothed or harmonically fitted series (e.g. a HANTS climatology): such curves suppress exactly the short, sharp changes this module is meant to find. Use the raw composite strds and let the module handle the gaps.

HOW EVENTS ARE DETECTED

For every clear observation at acquisition date AD, the value is compared with the last clear observation (AD-1) and, when lookback=2, also with the second-to-last clear observation (AD-2). An event is flagged when the change in the requested direction exceeds threshold. The comparison against AD-2 recovers events that would be missed when the immediately preceding date is cloudy.

Comparisons that span more than max_gap days are ignored, so a change measured across a long cloudy period (which reflects seasonal development rather than an abrupt event) does not trigger a false detection.

threshold_type sets how threshold is read:

  • absolute — in the value units of the data (default 0.2, suitable for NDVI).
  • relative — a fraction of the pre-event level.
  • mad — multiples of the per-pixel robust standard deviation (1.4826 × MAD) computed over the analyzed year. The robust scale is computed per year so that thresholds remain comparable between runs and are not affected by how many years or how many cloudy scenes are present in the archive. This option loads the year stack into memory, so keep the computational region to a reasonable size.

Change magnitude

Detection is triggered by the drop from the last one or two clear observations. The reported magnitude of an event, however, is measured against the pre-event level defined by baseline_window: the maximum (for drops) or minimum (for rises) of the last k clear observations before the event, with baseline_window=k.

With the default baseline_window=1 this is simply the immediately preceding clear value, reproducing Kolecka et al. (2018). With a larger window the magnitude is measured from the recent plateau, which is more robust when the single preceding observation is noisy or already slightly depressed. For example, with values 0.80, 0.78, 0.72 (a hazy scene) and then a cut to 0.50, the magnitude measured against the preceding value is 0.22, while against the recent plateau (0.80) it is 0.30, the latter reflects the true size of the event. This same pre-event level is used as the recovery reference R in baseline=observed mode, so magnitude and recovery share a consistent baseline: magnitude = R - trough.

Avoiding double counting

Because the AD-2 comparison reaches two observations back, a single event can be flagged twice: once at its own date and again one observation later (the value has not yet recovered, so the AD-2 span is still a large change). Kolecka et al. (2018) excluded such "overlapping events indicated at the same date or at subsequent dates, prioritizing" the single-interval condition.

This module reproduces that behavior with a day-based rule: min_separation (in days). Two detections closer than min_separation collapse into one, and the first (earlier) detection is kept, which corresponds to prioritizing the single-interval condition. The day-based form is cadence-independent: it stays correct when clouds stretch the real spacing, and it becomes a physically meaningful setting (the shortest plausible time between two genuine events). Choose a value shorter than the shortest real inter-event time; for grassland mowing, regrowth takes weeks, so the default (2 × step) safely removes the echo without merging genuine successive cuts.

RECOVERY

After each event the module tracks how far the signal returns toward a reference level. An event counts as recovered when the recovered fraction reaches recovery_target (default 0.8).

The reference depends on baseline:

  • observed — recovery toward the pre-event level R (see Change magnitude above). The recovered fraction is (value - trough) / (R - trough).
  • reference — recovery toward the level expected for the time of year, taken from a climatology strds (reference, a relative-time strds keyed by day-of-year). Recovery is measured as the closing of the anomaly (observed minus expected). The reference is used only for recovery, never for detection.

Each event resolves into exactly one of three outcomes, so that the counts partition cleanly (count = n_recovered + interrupted + n_incomplete):

  • recovered — reached recovery_target before the next event or the end of the series.
  • interrupted — a new event occurred before recovery completed. The maximum recovered fraction reached before the interruption is recorded (see mean_percent_restored). This answers the question "does the signal restore before the next event?".
  • incomplete — the event was still open at the end of the series (it simply ran out of observations). These are counted separately in n_incomplete and are excluded from mean_percent_restored, so that events late in the season do not bias the restored-fraction statistic downward.

OUTPUTS

All outputs are summary rasters written with the output prefix, one value per pixel (or, with vector, one value per parcel, constant across the parcel's pixels), masked to pixels that have at least one clear observation and to the current MASK:

  • <output>_count — number of detected events.
  • <output>_first_doy, <output>_last_doy — day-of-year of the first and last event.
  • <output>_mean_magnitude, <output>_max_magnitude — mean and largest event magnitude.
  • <output>_n_recovered, <output>_frac_recovered — number and fraction of events that recovered.
  • <output>_mean_recovery_days — mean time to recovery over recovered events.
  • <output>_mean_percent_restored — mean maximum recovered fraction (0-100) over interrupted events.
  • <output>_n_incomplete — events still open at the end of the series.
  • <output>_n_drops, <output>_n_rises — only with direction=both.

PARCEL-LEVEL ANALYSIS

t.rast.eventdetect detects events per pixel. Where the landscape is organized into management units (agricultural parcels, mown meadows, forest stands), analyzing those units instead of raw pixels is usually more accurate, because mixed and edge pixels are the main source of noise: Kolecka et al. (2018) found parcel and shrunken-parcel units more accurate than raw pixels for exactly this reason. There are two ways to work at the parcel level, and they answer different questions.

Detecting on parcels (vector)

Pass a parcel vector map with vector. Each observation is then reduced to a per-parcel median before detection, and the detection runs once per parcel instead of once per pixel. The summary rasters are written as usual, now constant within each parcel.

This is the most accurate route for parcels that are managed as one unit. Detection is a nonlinear threshold, so thresholding a denoised parcel-median signal is not the same as averaging the yes/no decisions of many noisy pixels (threshold-of-median is not median-of-thresholds). The parcel median also fills cloud gaps: a date still yields a value whenever enough of the parcel is clear, even when individual pixels are cloudy, so fewer observations are lost.

g.region raster=grassland_mask -p

t.rast.eventdetect input=S2_ndvi year=2021 output=mow vector=parcels \
  direction=drop threshold=0.2 lookback=2 recovery_target=0.8

The aggregation statistic is the median, which is robust to a few off-parcel or lingering-cloud pixels. min_clear sets how much of a parcel must be clear for a date to contribute (a fraction between 0 and 1): with the default 0 a single clear pixel suffices, while min_clear=0.5 requires a majority of the parcel to be clear.

Edge handling is a preprocessing choice rather than a module setting, which is why it is left to you: to work with "shrunken parcels" that exclude boundary pixels, buffer the parcel map inward first (v.buffer -s with a negative distance) and pass the buffered map as vector. This keeps the boundary rule, the aggregation statistic, and the clear-fraction rule under your control instead of fixing them inside the module.

Aggregating results to parcels (v.rast.stats)

Run the module normally on pixels, then summarize each summary raster into the parcel attribute table with v.rast.stats. Unlike the vector route, this keeps the per-pixel (sub-parcel) heterogeneity available: it does not collapse a parcel to a single signal, so you can still see how variable the response was within a unit.

Use the mean (method=average) for the continuous outputs (mean_magnitude, max_magnitude, frac_recovered, mean_recovery_days, mean_percent_restored) and a representative value for the integer count outputs (count, n_recovered, n_incomplete). v.rast.stats has no mode, so use the median (method=median) as the representative count; if you need a true majority, rasterize the parcels and use a raster mode tool.

t.rast.eventdetect input=S2_ndvi year=2021 output=mow \
  direction=drop threshold=0.2 lookback=2 recovery_target=0.8

v.rast.stats map=parcels raster=mow_mean_magnitude \
  column_prefix=mag method=average
v.rast.stats map=parcels raster=mow_count \
  column_prefix=n_events method=median

The same commands also work after the vector route: the summary rasters are then constant within each parcel, so any statistic (including method=average) returns that single parcel value.

If you need an aggregation statistic other than the median, or want to keep the parcel-median series itself, build it yourself before running the module: reduce each date to a per-parcel value (for example r.stats.quantile base=parcels cover=<index_map> percentiles=50 output=<parcel_median> for the median), register the results into a new strds, and run t.rast.eventdetect on that strds without vector.

Choosing between them

Use vector to maximize detection accuracy for parcels managed as one unit; it is also the cheapest of the parcel routes, because detection runs once per parcel rather than repeating the identical computation for every pixel of the parcel. Use v.rast.stats on per-pixel results when you want to keep sub-parcel heterogeneity. In both cases the choice of aggregation statistic (median, mean, trimmed) and of a clear-fraction rule are yours to set.

NOTES

The module runs on the current computational region and honors the current raster MASK. Set the region to the input maps before running.

The analysis is vectorized over space and loops over time, so cost scales with the number of maps, not the number of pixels; it is not a per-pixel Python loop. Memory holds only a handful of full-region layers (plus the year stack when threshold_type=mad).

To analyze management units rather than raw pixels, see PARCEL-LEVEL ANALYSIS above.

EXAMPLE

Detect grassland mowing events in an NDVI strds for 2021, using the Kolecka et al. (2018) rule set (0.2 drop, comparison to the last two clear observations), and characterize regrowth:

g.region raster=grassland_mask -p

t.rast.eventdetect input=S2_ndvi year=2021 output=mow \
  direction=drop threshold=0.2 threshold_type=absolute \
  lookback=2 min_separation=10 recovery_target=0.8

r.colors map=mow_count color=viridis
